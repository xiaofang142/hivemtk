## User Scenarios & Testing *(mandatory)*

### User Story 1 - 跨境电商客户统一主数据与跨账号检索（第一部分，Priority: P1）

作为跨境电商运营负责人，我需要把分散在多个业务账号、聊天记录里的客户/联系人/公司/供应商/服务商信息统一沉淀成一套主数据，并能按账号、员工、行业、权限隔离数据，去重、检索、导入导出、审计，从而从单账号和跨账号行业两个视角发现商机。

**Why this priority**: 这是全部线索与智能体能力的“数据底座”；没有统一主数据与权限隔离，后续线索归档、画像、推送都无处落地。用户明确将其列为第一部分。

**Independent Test**: 在一个租户内构造两个渠道账号、两个员工与重复客户数据；可独立验证：数据按账号/员工/行业隔离可见、重复客户被识别合并、单账号 360 视图与跨账号行业交叉检索返回结果、操作有审计记录、AI 画像/分层给出带证据的建议、线索发现后负责人收到推送。

**Acceptance Scenarios**:

1. **Given** 租户下存在多个渠道账号与员工，**When** 员工 A 查看客户列表，**Then** 仅看到其权限范围（账号/员工/行业）内的客户，越权数据不可见且接口返回 403。
2. **Given** 同一手机号/邮箱/外部 ID 在两个渠道账号出现，**When** 执行去重合并，**Then** 系统识别为同一客户并生成合并记录与操作审计，原始来源可追溯。
3. **Given** 客户存在公司、联系人、供应商、服务商、跟进记录、标签关联，**When** 查看单账号客户 360 视图，**Then** 展示完整链路且跨账号行业视角可检索到该客户的行业资源。
4. **Given** 线索被识别并归档，**When** 归档完成，**Then** 关联负责人收到站内通知（及配置的外部通知）。

### User Story 2 - 线索模块全链路审计与多规则并行检测（第二部分，Priority: P2）

作为渠道运营与线索负责人，我需要按「渠道 → 渠道下账号 → 通知人员」配置线索归档通知，按渠道/账号粒度配置独立线索发现规则，并通过关键词、语义关键词、LLM 三路并行检测 + 二次 LLM 总结判断（结合多轮对话与历史消息）发现商机，最后归档用户与线索信息并通知负责人。

**Why this priority**: 用户第二部分诉求，是“发现商机并通知”的核心闭环，依赖 US1 的客户主数据与 US4 的渠道账号地基。

**Independent Test**: 在单渠道内为不同账号配置不同规则与通知人，注入含关键词、语义命中、仅语义可判定的多轮对话；可独立验证：三路检测结果分别记录、二次 LLM 汇总产出线索类型、历史消息纳入判断、命中防抖去重、归档与通知按配置人员送达。

**Acceptance Scenarios**:

1. **Given** 渠道 A 与其下账号 A1、A2 分别配置不同规则，**When** A1 与 A2 各产生命中对话，**Then** 各自按本账号规则判定并通知各自配置的人员。
2. **Given** 一条消息同时命中关键词与语义，**When** 三路检测并行执行，**Then** 三路结果均落库为独立证据，二次 LLM 汇总给出统一结论与类型。
3. **Given** 当前对话仅含指代（如“这个能不能做”），**When** 判定时，**Then** 系统纳入多轮上下文与历史消息后判定，并在证据中引用所依据的历史消息。
4. **Given** 线索已归档，**When** 通知发出，**Then** 归档包含用户信息与线索信息，通知按「账号维护人 → 渠道维护人 → 租户默认」路由且记录送达结果。

### User Story 3 - 自动回复智能体与线索发现智能体解耦（第三部分，Priority: P3）

作为系统管理员，我需要把自动回复智能体与线索发现智能体彻底剥离：任意渠道账号接入后两者是独立模块；自动回复负责意图识别/NLP/情感识别/拟人工回复与转人工，线索发现只负责从双方对话中识别商机并归档，不干预自动回复；两者共享透明的对话历史与用户数据，允许交叉引用以丰富画像、标签与历史备注摘要。

**Why this priority**: 用户第三部分诉求，解决当前 ingest 后链路交织导致的互相干扰；依赖 US4 的渠道账号绑定与 US2 的线索归档。

**Independent Test**: 在同一渠道账号上分别启停两个智能体；可独立验证：关闭自动回复不影响线索发现产出、关闭线索发现不影响自动回复产出、两者读取同一份对话历史与用户标签、一方写入的标签/摘要可被另一方交叉引用。

**Acceptance Scenarios**:

1. **Given** 某账号只启用线索发现智能体，**When** 双方继续对话，**Then** 系统识别商机并归档，不产生任何自动回复下发。
2. **Given** 某账号只启用自动回复智能体，**When** 用户发言，**Then** 系统按意图/情感给出拟人工回复或转人工，不产生线索归档。
3. **Given** 两个智能体同时启用，**When** 自动回复产生一条“已转人工”备注，**Then** 线索发现判定可读取该备注作为上下文证据。

---

### User Story 4 - 渠道与渠道账号统一配置、识别码替换与三路消息合并（第四部分，Priority: P4）

作为系统管理员，我需要把散落的渠道/渠道账号配置统一到数据表驱动的管理界面：预设渠道可开启、单渠道多账号并配置各类信息、智能体绑定与账号数据授权统一收口、每个渠道唯一识别码一次性替换 bartoken 并被所有上报/桥接/hook 链路使用、渠道账号列表与自他识别封装为统一方法、三条消息收发路径（统一 API 收件箱 / 按账号均匀收发 / hook）合并治理。

**Why this priority**: 用户第四部分诉求，是 US2、US3 的技术地基；文档按用户要求排在第四，但实施排期必须最先落地其地基部分（见 plan.md）。

**Independent Test**: 在管理界面新增一个预设渠道与账号、生成/重置识别码、绑定两类智能体、配置账号负责人；可独立验证：所有渠道账号下拉来自统一方法、识别码替换后三条链路均用新码识别租户与账号、自他识别在单聊与群聊均正确、配置变更即时影响线索与自动回复行为。

**Acceptance Scenarios**:

1. **Given** 预设渠道表已存在，**When** 管理员开启一个渠道并新增账号，**Then** 该账号出现在所有渠道账号选择列表中，且可配置名称/备注/自他识别名称/两类智能体/数据授权。
2. **Given** 识别码已一次性替换 bartoken，**When** bridge、TG hook、三方 API 上报使用新识别码，**Then** 均能正确解析租户与账号；旧 bartoken 不再被接受（无兼容期）。
3. **Given** 同一渠道账号在单聊与群聊各有一条消息，**When** 调用统一自他识别方法，**Then** 单聊按双方账号、群聊按成员角色正确区分自己/他人。
4. **Given** 三条消息路径并存，**When** 消息进入，**Then** 统一落入同一收件箱模型，按识别码归属到正确渠道账号。

---

### Edge Cases

- 同一客户在多个渠道账号重复出现且合并后又被拆回：需保留完整合并/拆分审计链。
- 同一账号既是需求方又是供应方：线索类型判定需支持多角色，归档时不要互相覆盖。
- 三路检测中 LLM 超时/不可用：需降级为关键词+语义结果并标记证据不完整，不得静默丢弃。
- 群聊中自己发送的消息与历史消息混杂：自他识别与上下文聚合需排除机器人自身消息或明确标注。
- 识别码重置瞬间有在途消息：需保证重置前后在途消息按旧码仍可归属（一次性替换无兼容期，但需处理在途窗口，方案见 plan.md）。
- 通知人员为空：按「账号维护人 → 渠道维护人 → 租户默认」兜底，仍为空则记录“无通知人”审计。
- 导入导出含敏感字段：需按权限过滤导出范围，导出行为写入审计。
- AI/RAG 检索命中敏感客户信息：需遵循数据隔离，不得跨权限泄漏。

## Requirements *(mandatory)*

### Functional Requirements

**第一部分（CRM）**

- **FR-001**: 系统 MUST 提供客户、联系人、公司、供应商、服务商、跟进记录、标签的统一主数据管理（CRUD）。
- **FR-002**: 系统 MUST 按账号、员工、行业、权限维度隔离数据可见性，越权访问返回 403。
- **FR-003**: 系统 MUST 支持基于手机号/邮箱/外部 ID/名称相似度的客户去重与合并，并记录合并来源与审计。
- **FR-004**: 系统 MUST 支持客户数据的搜索、多条件筛选、导入与导出，并按权限过滤导出范围。
- **FR-005**: 系统 MUST 记录所有客户主数据的新增、修改、删除、合并、导入导出操作审计。
- **FR-006**: 系统 MUST 提供单账号客户全链路 360 视图与跨账号行业资源交叉检索。
- **FR-007**: 系统 MUST 接入 AI/RAG 产出客户画像、分层、商机识别与跟进建议，且每条建议附可追溯证据。
- **FR-008**: 线索归档后系统 MUST 将线索关联到客户并将负责人推送通知。

**第二部分（线索）**

- **FR-009**: 系统 MUST 支持「渠道 → 渠道下账号 → 通知人员（一个或多个）」的配置。
- **FR-010**: 配置人员登录后 MUST 仅看到其权限内的渠道客户列表与消息列表（数据列表）。
- **FR-011**: 系统 MUST 支持线索发现规则在“全局共用/按渠道/按渠道下账号”三个粒度配置，规则含关键词、语义关键词、系统性描述语。
- **FR-012**: 系统 MUST 并行执行关键词检测、语义关键词检测、LLM 调用检测，三路结果各自落库。
- **FR-013**: 三路结果后系统 MUST 再调用一次 LLM 做总结判断，产出是否线索与线索类型，并纳入多轮对话与历史消息。
- **FR-014**: 系统 MUST 对重复/高频命中做防抖与去重。
- **FR-015**: 线索归档 MUST 包含用户信息与线索信息，并按配置路由通知负责人、记录送达结果。
- **FR-016**: 系统权限设计 MUST 综合考虑渠道、渠道下账号、权限模块，除 RBAC 外补充数据权限维度；原 RBAC 模块 not be modified（用户明确）。

**第三部分（智能体剥离）**

- **FR-017**: 自动回复智能体与线索发现智能体 MUST 为两个独立模块，可独立启停。
- **FR-018**: 自动回复模块 MUST 支持意图识别、智能体、NLP、情感识别、拟人工回复、下发/返回/转人工。
- **FR-019**: 线索发现模块 MUST 只处理商机识别、类型判定、用户与线索归档，不触发自动回复。
- **FR-020**: 两模块 MUST 共享同一份用户数据与对话历史，并允许交叉引用标签/备注/摘要。
- **FR-021**: 群聊场景 MUST 支持多成员对话上下文聚合。

**第四部分（渠道/账号/识别码）**

- **FR-022**: 预设渠道 MUST 基于数据表配置，新增渠道只需一次配置即可全系统生效。
- **FR-023**: 用户 MUST 能选择开启哪些预设渠道，并对渠道及渠道下账号做增删改查。
- **FR-024**: 渠道账号 MUST 能配置名称、备注、自他识别名称、接入的自动回复智能体、接入的线索发现智能体、账号数据授权。
- **FR-025**: 原智能体管理中与渠道账号绑定的逻辑 MUST 移除并统一到渠道账号管理。
- **FR-026**: 「线索发现」 MUST 改名为「线索发现智能体」，具备列表/新增/修改/删除。
- **FR-027**: 散落的渠道账号配置 MUST 集中到渠道账号管理，不同类型渠道账号可配不同信息。
- **FR-028**: 每个渠道 MUST 有唯一识别码，支持重置，一次性替换 bartoken；三方 API、bridge、TG hook/轮询、SageX 均基于该识别码。
- **FR-029**: 系统 MUST 提供基于渠道账号管理的统一渠道账号列表/下拉/选择方法，所有内部调用统一走该方法。
- **FR-030**: 系统 MUST 提供基于渠道账号+唯一识别码的统一自他识别方法，区分单聊与群聊。
- **FR-031**: 三条消息路径（统一 API 上报+统一收件箱 / 按账号均匀收发 / hook 收发）MUST 合并治理，不分散实现。

### Key Entities *(include if feature involves data)*

- **Customer（客户）**：统一客户主数据；扩展来源字段、账号/员工/行业归属；关联 OneID、公司、联系人、标签、跟进记录、线索。
- **OneID / Merge（身份合并）**：跨账号身份归一与合并审计记录。
- **Company（公司）**：扩展既有公司域（迁移 053 + 079 演进，已有 `model/company.go` 与 `service/company.go`），关联客户/联系人；不重复新建。
- **Contact（联系人）/ Supplier（供应商）/ ServiceProvider（服务商）**：全新实体，挂接客户与渠道账号。
- **Channel（渠道）/ ChannelAccount（渠道账号）**：统一渠道与账号主数据；含唯一识别码、类型、智能体绑定、负责人、数据授权。
- **ChannelIdentifyCode（唯一识别码）**：替代 bartoken，支持重置，被所有链路使用。
- **LeadMiningRule（线索发现规则）**：三粒度（全局/渠道/账号）+ 关键词/语义/描述语。
- **LeadMiningJudge / Hit / NotifyRoute**：三路检测证据、二次 LLM 结论、通知路由与送达记录。
- **Clue（线索）**：扩展归档字段（用户信息、类型、角色、来源消息、上下文证据）。
- **ConversationContext（对话历史）**：单聊双向与群聊多成员消息，供两智能体共享交叉引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 租户内客户去重准确率 ≥ 95%（人工抽样 100 条重复/非重复标注）。
- **SC-002**: 权限隔离有效性 100%——越权访问客户/消息列表一律被拒且无数据泄漏。
- **SC-003**: 线索判定中，纳入多轮/历史上下文的用例比例 = 100%，且二次 LLM 结论在抽样中可解释（附证据）。
- **SC-004**: 三路检测各自独立留证率 100%，LLM 不可用时降级不丢结果。
- **SC-005**: 识别码替换后，三条消息路径均用新码识别，旧 bartoken 识别成功率 = 0%。
- **SC-006**: 系统内渠道账号列表/自他识别调用收敛为统一方法，重复实现数 = 0。
- **SC-007**: 自动回复与线索发现各自独立启停互不影响，交叉引用可用率 100%。
- **SC-008**: 归档通知到达配置负责人的比率 100%，无通知人场景有兜底与审计。
- **SC-009**: 全部新增/修改 API 通过 `scripts/api_verify_full.py` 三端验证（入参/返回/预期/DB）。

## Assumptions

- 用户已确认的四项决策（见“范围与路线说明”）为本规格硬约束。
- 现有认证（登录态/租户上下文）与 RBAC 模块保持不变；数据权限作为新增维度叠加，不修改原 RBAC 代码。
- 测试库密码需显式导出 `POSTGRES_TEST_PASSWORD`（不从 `.env` 读），否则测试会被 `t.Skipf` 假绿跳过。
- 平台第三方调用成败以业务码判断，不以 HTTP 状态码判断（宪法原则 IV）。
- 移动端不在本仓范围；前端改动限于 user-web（管理端）。
- 一次性替换 bartoken 意味着旧客户端需随本特性同步升级；在途消息窗口的处理方案见 plan.md（非“兼容期”，仅为原子切换窗口）。
- 新功能实施仍需按宪法在闸门处人工评审，`on_reject: abort`；本轮仅产出文档，不进入 implement。

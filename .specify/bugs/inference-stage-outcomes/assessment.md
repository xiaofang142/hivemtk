# FA-AGENT-RUN-01 阶段失败与可发布状态

- 日期：2026-11-20
- 结论：valid，源码确认，等待真实调度故障回归红灯。

## 根因与影响

`InferenceCycle.RunOnce` 只记录 StageResult.Error，随后仍以 nil error 提前结束并 finish 检查点；已有 Plan 会被计为成功。编排器丢弃 Stages，HTTP 错误也不保留阶段诊断。流式入口另有四阶段实现，缺少 reviewer。默认 reviewer 将技术错误当继续，复核 Passed=false 也不阻止后续发布。

## 方案论证

采用一个五阶段调度器，普通和流式共用。每个实际执行阶段只有一条规范化记录；保留阶段已有业务动作，技术错误以稳定代码公开，原始原因只用于错误链和服务日志。阶段 Error、截止时间、无效结果及缺失硬闸/复核端口均停止后续阶段，清除可外发内容并返回 error。拒绝是已决业务结果，不冒充技术成功或可发布回复；正常转人工是决策意向，不表示已建单或已发送。可选记忆/检查点故障明确标记 degraded，不吞为完全成功。

成功阶段可落续跑点；失败不推进游标、不标 done，将失败尝试附记在最后成功快照之外，重试重新执行失败阶段。保留合法安全转人工的提前结束行为。流式失败只产生失败终态并关闭内置通道，不发成功 complete。返回结果、统计、HTTP 与检查点诊断使用同一 outcome/stages。

不采用逐处补日志/仅 HTTP 改状态，因为无法消除流式遗漏、错误成功统计及错误检查点。阶段调用仍同步且必须遵守 context，不用遗留 goroutine 伪造强制终止；即使协作超时后返回 Continue，也按超时失败处理。进程 panic 的原有中断/续跑语义保留。

## 验收与边界

逐五阶段注入 Error、协作超时、复核拒绝、错误后恢复，核对没有发布/工具/人工副作用、统计分类、可查阶段和检查点不越过失败点；真实 HTTP 入口核对失败响应及阶段诊断。另测合法转人工、可选端口降级、流式包含复核与通道关闭。使用本地计数端口和检查点替身，不访问第三方。RUN-02 的规划/执行契约、RUN-03 的发布/交接可靠受理、CKPT-01 的账号配置指纹隔离各自独立，不在本项宣称完成。

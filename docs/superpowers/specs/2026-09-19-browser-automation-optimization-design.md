## 二、纪律与验收总则

1. 每项动手前全网调研同类实现（browser-use/Stagehand/Postiz/Midscene/xiaohongshu-mcp/MDN/Chrome 官方），结论写入 spec 附录"调研台账"；与 P0 前提/铁律冲突的方案一票否决。
2. 新增测试先反向验证（还原缺陷应红）；`go test ./...`（注意测试库口令漂移）、两包 vitest 全绿才算批完成。
3. 扩展行为变更：三处版本锚点同升 1.4.2→1.5.0（src manifest / dist manifest / nm-host hostVersion）+ `check_browser_host.sh` 动态提取验证。
4. 真机 e2e（批5）：A 链路任务集 = xhs snapshot→markdown→post_comment 三段式、douyin/xianyu 读链路、cron 与 MCP 入口各一、Brain 模式一例；以 `GET /sessions/:id/export` 审计包逐项核验 + CDP 事件时间线复核拟人节奏。B 链路 = 双消息连发验 B1、交叉会话 ack 验 B2、限流单例验 B6。
5. 全程不 commit；结束后交用户真机回归，回归通过再按显式路径提交（共享工作树纪律）。
6. 未证伪不删除：一切"死代码"处置仅限降级标注/停止调用，物理删除需另行拍板。

## 附录一：调研台账

| 项 | 同类实现 | 结论 | 落地决策 |
|----|---------|------|---------|
| B1/B2 | Azure Architecture Patterns "Idempotent Consumer"：消费/回执判重必须用跨副本稳定的复合键；内容哈希键需与消息路由维度（会话）组合 | 判重键 `msg_id` 必须由 bus 与 DB 两路同一构造（`ContentHashMsgID` 已跨语言对齐：Go `webhook_dedup.go:103` ≡ JS `types.js contentHash`）；ack 若无 conv 则同内容跨会话必然互翻 | bus 事件统一走 `BuildOutboundSSEEvent`（含 msg_id）；扩展 `resolveSSEOutboundKeys` 缺失时 fail-loudly 用 contentHash 兜底；ack v2 携带 `items[{msg_id,conversation_id}]`，legacy 路径保留+Warn |
| B3 | WHATWG SSE 标准：`retry:` 仅设定 EventSource 重连间隔，不背历史；Socket.IO / LaunchDarkly 断线实践：达到重试上限后"降级为轮询"而非永久放弃；AWS Architecture Blog：退避必须带抖动（full jitter）防惊群 | 永久 break 是反模式；`retry:` 收而不应用是半实现 | 客户端 attempts>MAX 后转降级周期重连（base=max(5min, serverRetryDelayMs)+0~20% 抖动），快速阶段保持本地指数退避（1s→30s，×(0.5+rand·0.5)）；服务端条件化 `poll.Reset`（总线活跃期拉长轮询），修死"心跳无限续期导致兜底轮询永不触发" |
| A3 | AWS SDK Go v1/v2 重试契约：分类未知错误一律按不可重试处理（"all-Unknown → no retry"），防止对永久性故障烧重试预算 | "默认失败"是业界共识，本项目文档 §4.6 亦已明文 | `ClassifyError` default → 新增 `ErrUnknown`（非重试）；显式白名单（timeout/超时/未就绪/element_not_found）才 Retry——中文「超时」先入白名单再翻转 default，防 Host 命令超时误伤 |
| A1 | BrowserUse Stagehand `selfHeal`：定位失败→拍 a11y 树→LLM 按 ref 重定位，**只回写缓存不回写代码、且限一次**防预算失控；Cloudflare Browser Rendering 同型 | 双重维护与无降级是选择器脆断根因；一次性自愈+结构化 `selector_miss` 是成熟范式 | 定位知识收口单表；扩展注入失败返回 `selector_miss` → Go 侧 a11y snapshot + LLM 按 ref 重定位一次（批2 实施） |
| A2 | MediaCrawler / spider 系风控：拦截判定分层——URL 重定向特征（`/website-login/error`、`/captcha`）、风控专用 DOM 容器、响应错误码（461/`verify_type`）；**全文子串匹配是公认反模式** | 正常内容含"验证码"必误报；判定必须收窄到结构化信号 | `DetectBlock` 仅匹配 URL 模式与专用容器选择器，文案 marker 不再扫快照全文（批2 实施） |
| B7 | xiaohongshu-mcp / browser-use：CDP `Input.dispatchKeyEvent` 逐码点+对数正态间隔+贝塞尔轨迹（A 侧已实现）；contenteditable 网页（bridge 侧）无法用 CDP 穿透扩展进程，MDN：`execCommand('insertText')` 是扩展内容脚本保持框架同步（React/Vue 受控值）的兼容路径，`isTrusted` 对合成事件恒 false 是平台限制而非缺陷 | 两链路拟人参数应单一来源；bridge 侧拟人=逐段 insertText + 随机间隔 + 穿插鼠标活动，不伪造 trusted 事件 | 抽 `packages/browser-core/` 纯函数包（键击分布/轨迹/抖动/参数表），A/B 两侧各自引用、manifest 与注入通道不合并（批2 实施） |

## 附录五：批4 挂账项调研定论（2026-09-19，只出结论，实施留 v2 拍板）

- **A7 提示注入 v2 加固 → 结论：做「信封净化 + Brain 动作白名单」，否决文案启发式**。实测事实（file:line 为准）：`<page_snapshot>` 信封只在两处施加（`brain.go:182`、`executor_selfheal.go:78`），而 **goal 原文直拼**（`brain.go:179`，prompt 里承诺的 `<user_request>` 分隔符全仓不存在）、reflect 的 `memory` 字段未包裹（`brain.go:184-192`，等于给 LLM 一条自造洗稿通道）、`SummarizeSession` 把 `extracted_data` 里的页面文本零分隔符入 prompt（`brain.go:301-304`）——信封可被页面文本自行闭合伪造，`internal/browser_automation` 全包无任何 sanitizer。动作面：Brain plan 走裸 `json.Unmarshal`（`executor.go:454`），dto 的 `oneof` 词表只在 gin 绑定生效，越词动作靠 dispatch 的 `未知动作` fail-closed（`executor.go:843`）挡住；**但词表内、prompt 仅口头禁止的动作仍可执行**——`open_tab` 任意 URL（只查 scheme）、`click_near`（不在 planActionTable 内），且 target 接受任意 CSS 而非仅限快照 ref；最宽的是自愈路径：`resolve_ref` 原样回吐非 `@e` 输入（`primitives.js:527`）、heal 只拒空串（`executor_selfheal.go:100-106`），LLM 自选的 `send_button_text` 直接决定不可逆点击目标（`executor_selfheal.go:121-127`）。**注**：「步值全部来自用户任务」的前提对 Brain 模式不成立——该模式丢弃任务 steps（`executor.go:243`），`step.Value` 即 LLM 输出。落地面 3 处：单一 rune 级净化（`<`/`>`/`@e\d+`）施于两处信封、Brain 侧动作 allow-list + 「target ∈ 快照 refs ∪ 适配器选择器」成员校验（照抄 screenshot 的硬闸先例 `executor.go:489-496`，并剔除 open_tab/click_near）、heal 侧 `^@e\d+$` + 名字必须在快照内。同类实现佐证同一取向：browser-use 在**解析期**而非 prompt 期设闸（`AgentOutput(extra='forbid')` + registry 动作表，未知动作/参数直接 raise），Midscene 默认拒绝能力位（如 `fileChooserAllowedDir`，官方理由即"限制幻觉与页面注入"），两者都不做文案启发式（误报代价高于收益）。
- **A8 send 45s 慢回包根治 → 结论：45s 不是拟人预算，是协议/宿主拥塞；做「SW 内 CDP 流水线」，不做所谓批量 API**。逐段实测计数：一次 `comment_send` = 1 帧下行 + 1 帧上行（nm-host 是哑管道，`host_registry.go:261-295`）+ SW 内 1 次 `executeScript` 定位（15s raceTimeout 上限）+ **12–42 个串行 await 的 `chrome.debugger.sendCommand`**（鼠标 trail 10–40 个 mouseMoved + pressed + released，`input.js:104,150-165`），全程零 `Runtime.evaluate`/DOM.getDocument，且 **send 段不含任何键击**（逐码点键入在 prep 段、30s 预算下）。拟人下限算得：trail 70ms + settle 300 + hold 84 + afterClick 400 ≈ **中位 1.36s / 最坏 4.2s**——45s 只能是「每次协议调用 1.1–3.5s」的拥塞。现网自证：`user-server.log` 有 10 条 `Host 命令超时（45s，action=comment_send）`，其中一条 5 码点评论烧满 45s；同原语另一 session（10 码点）整步 12.1s → 4× 离散。**前置条件（必须先做）**：`Request` 与 comment_send 回包加分相位耗时（当前只有步级 `duration_ms`，`executor.go:602-615`，无法归因）。CDP 侧无批量 API（`Input.*` 无 batch，`autoRepeat` 每次一调用无收益，`Runtime.evaluate` 赋值 `isTrusted:false` 已被 B7 一票否决，多命令合并 WS 帧是空操作因为本就一命令一帧）。最高杠杆改法：**trail 的 mouseMoved 不 await ack**（单 debugger session 保序），pressed/released 继续 await（错误/断线检测点），并给每个事件显式 `timestamp`（需真机核 Chrome 1.3 协议字段语义），使拥塞时突发刷入仍保留真实事件间隔。风险=不加 timestamp 时 trail 在拥塞下塌成同一时刻→拟人度受损。附带发现（与 D7 交互）：debugger 3s 空闲自动 detach（`input.js:95-101`）意味着确认闸门挂起 ≥3s 后必重 attach（+500ms），且单次 45s 超时已达 host 病态探针阈值一半→可触发 `__host_shutdown__` 杀宿主（`host_registry.go:302-316`）。
- **A9 断点续跑 → 结论：否决通用「尾步续跑」，只保留「重跑不双发」的证据闸（约 3 行，不需新表）**。安全性盘点（dispatchStep 逐 case）：只读=assert/query/snapshot/markdown/wait_for_selector/extract；幂等=wait、type（有内容先清空，`submit_on_enter` 例外转不可逆）；上下文依赖=click/click_near（可翻转点赞关注）、scroll（相对位移累加）、screenshot（抢焦点+落盘）；对会话不可逆=close_tab；`post_comment`=不可逆单次提交。**决定性事实**：除 open/close_tab 外每个 case 都用 `session.ChromeTabID`（`executor.go:681`），崩溃后该 id 必失效→唯一合法入口只有 open_tab；且 `Request` 在 WS 关闭/超时时直接放弃在途命令（`host_registry.go:276-284`）→ **`failed` ≠ 未发生**，「从第一个非成功步续跑」在写步上构造性不安全。现网量化（本机 psql 读 user_db）：164 个显式编排 session 中 86 个含失败步、45 个提前中止、累计未执行 152 步（收益≈3.4 步/session）；post_comment 失败 18 条里 8 条 `unknown_action`、2 条 `comment_input_not_found`（从未点击，真安全），仅 2 条 send 超时=结果未知；带证据的 4 个 session 全部 `verified=true`、0 个 false。最小落地：`mergeExtract` 证据补 `step_index`（现只有 text/send_error/verified/evidence/posted_at），重下发时跳过同序号 `verified=true` 的写步，`verified=false`/缺证据→不重发、fails-loudly 转人工（Postiz markUnconfirmed 语义）。两处硬缺口需一并认账：重下发走 `RunTask` 新建 session（`task.go:324-332`）既不继承 `extracted_data` 也无跨 session 步查询（`repository/step.go:13-20` 只有 `ListBySessionID`）；`command_log` 90 天裁剪（`retention.go:26,45`）使「事件日志重放」本就不 durable。同类对照：Stagehand 官方 best-practices 明确失败不续跑（重跑或清缓存）；browser-use 文档站本次未能定位 replay/resume 章节（诚实标注，不作依据）。**需真机复核**：`verified=false` 现网样本为 0，写步跳过逻辑必须等批5 造出 session179 型 send 超时才能证伪。

# 功能模块市场：UI 与信息架构论证（任务四交付）

> **状态**：v1.0 · 2026-10-18
> **需求原文**：「参考资产包市场，设计功能模块市场……**功能模块市场要论证合理UI，组织架构**」
> **实现**：`user-web/src/views/moduleMarket/{Market,Detail,MyModules,Orders}.vue`
> **清单依据**：`MODULAR_MODULES.md`

---

## 一、为什么必须论证而不能照抄资产市场

资产市场与功能模块市场**看起来都是「卡片列表 + 购买」**，但它们卖的东西性质不同：

| 维度 | 资产市场 | 功能模块市场 |
| --- | --- | --- |
| 买的是什么 | **数据**（话术/人设/AB 方案，行业模板） | **能力**（一段长期生效的功能 + 权益） |
| 交付形态 | 立即到账（下载即得） | 订单确认后才开通 |
| 有无依赖 | 资产之间基本独立 | 模块之间有**依赖图**（买 GEO 会带出知识库） |
| 有无期限 | 无（一次购买永久可用） | 有（到期需续费） |
| 买了之后 | 资产列表里多一条 | 侧栏多出一个菜单分组 |
| 用户决策时长 | 秒级（便宜、试错成本低） | 分钟级以上（贵、影响面大） |

**结论**：照抄资产市场的 UI 会漏掉三件事 —— **依赖闭包、开通后侧栏变化、到期**。
下面每一条 UI 决策都对应其中之一。

## 二、信息架构（IA）

### 2.1 入口位置：为什么放在「系统设置」顶级下

```
系统设置
├── 站点配置 …（部署级，admin-only）
├── 团队 / 权限设置 / 资产包
└── 功能模块           ← 新增，与「团队/权限设置/资产包」平级
    ├── 功能模块市场    /module-market
    ├── 我的模块        /module-market/my
    └── 模块订单        /module-market/orders
```

| 候选位置 | 为什么不选 |
| --- | --- |
| 新建顶级分组 | 商业化只有 1 个顶级项，撑不起一个分组；且会让 7 个分组变 8 个，侧栏更挤 |
| 放进「AI 智能体」等业务分组 | 它横跨 24 个模块中 17 个，放任何一组都在暗示「它只管那一块」 |
| 放进「站点配置」下 | 站点配置是部署级、admin-only；「去开通功能」是租户管理员的**日常**动作，位置越浅越好 |
| 放顶部工具栏 | 与既有的"全局搜索/通知"层级冲突，且不承载父子关系 |

**关键约束**：`功能模块` 这组归属 **platform-link（基础模块，恒开）**。
它**不能**绑到任何付费模块 —— 否则「关掉 GEO → GEO 的市场入口消失 → 用户再也找不到开通 GEO 的地方」，
而未开通 GEO 的人恰恰最需要这个入口。这条反直觉的设计由
`TestModuleMarketAlwaysReachable` 钉死。

### 2.2 四个页面的职责边界

| 页面 | 回答的问题 | 决策成本 | 数据源 |
| --- | --- | --- | --- |
| **市场** `Market` | 「有什么、要不要、多少钱」 | 发现 → 决策 | `GET /api/module-market/list` |
| **详情** `Detail` | 「买了具体能用哪些页面」 | 决策 | `GET /api/module-market/detail/:key` |
| **我的模块** `MyModules` | 「我现在有什么、余额多少」 | 运维 | `GET /api/modules/my` + `/api/llm/wallet` |
| **模块订单** `Orders` | 「我买的东西到哪一步了」 | 追踪 | `GET /api/module-market/orders` |

**为什么市场与我的模块要分开**：资产市场里「我买了什么」也在同一个页面（资产市场有"我的资产"Tab），
但功能模块的「已拥有」会**改变侧栏**，把它和「未拥有」混在一页会让用户反复确认自己到底买没买。
分开后，**已拥有的入口在侧栏常驻、未拥有的在市场里**，心智是单向的。

## 三、UI 论证：六处关键决策

### 3.1 市场卡片：三档价格口径，绝不合并

| 模块形态 | 按钮文案 | 为什么这样写 |
| --- | --- | --- |
| 基础模块（`free=true`） | 「已包含」**禁用** | 它本来就可用。给一个"订阅"按钮等于**暗示要花钱**，会引发投诉 |
| 收费 0 元（`free_to_enable`） | 「开通」绿色 | 要开通、不收钱。与"免费"必须区分：前者会产生订单与权益，后者不会 |
| 收费 > 0 | 「订阅 · ¥128/年」 | 明码标价 |

> 若把 0 元也写成"免费"，用户点了才发现要提交订单等确认 —— 这是**最容易被投诉的一处**。
> 因此 `priceLabel()` 用三个分支而不是一个 `price>0 ? ... : '免费'`。

### 3.2 卡片上的「含 N 个页面」

**为什么必须显示**：功能模块不是"参数"而是"一整片菜单"，用户无法凭名称想象它包含什么。
把页面数摆出来，是把抽象商品变成可核对清单的最低成本做法。
详情页进一步列出 `菜单 key → 标题 → 路径`。

**为什么不直接列路径**：市场卡片上列路径会让卡片高度参差，且用户真正关心的是"能干什么"
而不是 URL。详情页展开即可。

### 3.3 订阅确认弹窗：必须展示依赖闭包（两层）

弹窗里明确分成三段：

| 段落 | 内容 | 来源 |
| --- | --- | --- |
| 将自动开通（免费） | 基础依赖，如 `knowledge` | `detail.auto_enabled` |
| **需另行订阅** | 付费依赖，如 `ai-agent` | `detail.payable_dependencies` |
| 联系方式 | 电话/邮箱 | 必填其一 |

> **付费依赖绝不自动开通**（平台端 `ModuleGrantService.walkDeps` 已按此实现并有测试）。
> 自动开通付费依赖 = 意外收费，是商业化最容易踩的雷。
> 反过来，基础依赖必须自动带出，否则用户买完发现用不了。

### 3.4 付款指引：一次也不省

下单成功后的提示**必须**包含联系方式，且由**后端下发**
（`GET /api/module-market/payment-guide` → 平台端 `site_contact_config`）。

理由：运营换微信号后，所有用户的付款指引自动跟着变。若写在前端，用户看到的是**过期联系方式**，
而这类问题的表象是"用户付了钱但没开通"，排查成本极高。

失败降级链：**平台返回的文案 → 用户端兜底常量**，任何情况下都非空
（`TestPaymentGuideNeverEmpty` 钉死：空串等于"订单已提交但没人知道找谁付款"）。

### 3.5 4301 的全站统一引导（`utils/request.js`）

用户深链到未开通模块的页面 → 后端返回 `HTTP 200 + code 4301`
（符合本仓"业务码进响应体"的错误通道约定）→ 拦截器识别 →

1. 提示「功能模块「X」未开通，请在功能模块市场订阅后使用」
2. 3 秒后跳 `/module-market?highlight=X`
3. 市场页**自动放开筛选条件**并把那张卡滚动到视野中央、加描边

> 为什么不在拦截器里直接跳转：用户可能是**误点别人发的深链**，直接跳走会丢上下文。
> 给 3 秒缓冲 + 可关闭提示，既给了原因也留了退路。

### 3.6 「我的模块」页承载 LLM 余额

需求五要求"实时扣减剩余 token 数"。但**实时扣减对用户是否可感知，取决于他能不能看到剩余量**。
后端 `/api/llm/wallet` 与 `/api/llm/plans` 在第三轮审核前**前端零调用** ——
计量做了一整套，却没有任何人看得见。现在「我的模块」页顶部是余额卡（剩余输入/输出 token + 累计消耗），
右侧直接是套餐购买入口。

## 四、与资产市场的复用与差异

| 维度 | 复用 | 差异 |
| --- | --- | --- |
| 卡片网格 + 分类筛选 | ✅ 沿用 | 增加「仅未开通」开关与来源/价格档 |
| 详情页 | 结构类似 | 增加**包含页面清单** + **依赖闭包** |
| 我的资产 | — | 拆为独立的「我的模块」页（见 §2.2） |
| 订单 | — | 新增独立页面；资产走积分即时到账，无订单态 |
| 付款 | 积分扣减 | 线下人工确认（本期无支付通道） |

## 五、可访问性与文案一致性

- 卡片按钮的禁用态用 `disabled` 而非隐藏：禁用保留"它存在但我不能用"的信息，隐藏会让人以为系统缺功能。
- 所有价格文案走同一个 `priceLabel()`，避免同一模块在不同页面显示不同价格（对账类投诉的常见来源）。
- 平台未连接时，市场页顶部 `el-alert` 明确说明「基础能力不受影响」，而不是只说"不可订阅" ——
  否则离线用户会以为整个系统坏了。

## 六、已知取舍

| 取舍 | 理由 |
| --- | --- |
| 不做套餐包 | 会把 17 个增值模块压成 1 档，运营失去颗粒度（见 `MODULAR_MODULES.md §5.1`） |
| 不做「试用」按钮 | 一期无支付链路，"试用"意味着要有到期与回收逻辑，会与"人工确认"模型冲突 |
| 市场不做搜索后端分页 | 24 个模块一次全量返回；引入分页只会在扩容（数百模块）时才需要 |

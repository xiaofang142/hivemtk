# 数据主体权利（DSAR）现状与删除权缺口

> 登记：未完成任务清单 G-8（观察项）。本文档是该项的持久化落点；
> 任何把"删除权已实现"当作既成事实的引用都是错误的——当前只有导出，没有删除。

## 已实现：导出权（DSAR export）

- 入口：`GET /api/auth/gdpr/export/:customer_id`（`user-server/internal/controller/data_export.go`）
- 实现：`DataExportService.Export / ExportJSON`（`user-server/internal/service/data_export.go`）
- 语义：按 customer_id 汇总该主体数据为结构化包，供用户取走。

## 未实现：删除权 / 被遗忘权（erasure）

当前**没有**任何按数据主体请求抹除个人数据的流程：

- 无 erasure API、无匿名化（anonymization）作业、无删除审计台账。
- 现有的"删除"均为业务删除（软删/租户隔离），不构成法律意义上的被遗忘权响应。

## 为什么不直接做掉（决策登记，2026-11-09）

1. **法域定位未定**：PIPL / GDPR / 其他的适用与豁免（如留存义务、完成交易所需、
   法定账务留存期）需要法务/产品拍板。盲删会破坏审计链与引用完整性，
   在有留存义务的法域反而是违规。
2. **删除语义需逐表设计**：聊天/账单/日志等表的"删除"是硬删、软删、还是匿名化，
   各表答案不同；需要一份保留期矩阵（retention schedule）作为前置输入。
3. 因此本项定为**观察项**：文档化维持，不擅自实现。升级为修复的前置条件：
   产品确定法域定位 + 保留期矩阵 → 立项时再设计 erasure 流程与审计。

## 现状下的风险缓解（已核实）

- 租户隔离：tenancyidx 全局 callback 强制注入 `tenant_id`（读路径），跨租户读不可达。
- 密钥面：APIKey 经 dbencrypt 密文存储；无硬编码密钥（E-3 扫描 0 命中）。
- 导出口本身挂鉴权（非匿名面）。
